# Список задач — Android-приложение на Python/Flet + Supabase

Учебный проект (ПК-2): мобильное приложение «Список задач» с CRUD в облачной
базе, сборка `.apk` — в GitHub Actions, без локального Android SDK и Flutter.

**Стек:** Python 3.13 · Flet 1.0.5 (клиент, Flutter под капотом) · Supabase
(PostgreSQL как Backend-as-a-Service) · supabase-py 2.29 · GitHub Actions.

Промежуточного сервера нет: клиент обращается к таблицам Supabase напрямую
с `anon`-ключом, поэтому доступ к данным ограничен RLS-политиками.

---

## Структура репозитория

```
.
├── .github/workflows/build-apk.yml   # сборка .apk в облаке
├── db/schema.sql                     # таблица + RLS-политики (Supabase SQL Editor)
├── src/
│   ├── main.py                       # экран Flet: только интерфейс
│   ├── repo.py                       # доступ к Supabase: только данные
│   ├── config.example.py             # шаблон ключей → копируется в config.py
│   └── assets/icon.png               # иконка приложения
├── tests/smoke_ui.py                 # проверка UI без сети (опционально)
├── pyproject.toml                    # зависимости + настройки flet build
├── requirements.txt                  # то же для локального pip (см. ниже)
├── .gitignore                        # src/config.py исключён
└── README.md
```

Почему так: `main.py` ничего не знает про SQL и HTTP, `repo.py` — про кнопки.
Такое разделение позволило менять запросы, не трогая экран, и наоборот.

## Как это работает

```
Экран Flet (Python)  ──supabase-py──►  Supabase REST API  ──►  PostgreSQL (tasks)
        ▲                                                            │
        └──────────────── JSON-ответ ◄──────────────────────────────┘
```

Таблица одна — `tasks`:

| поле | тип | смысл |
|---|---|---|
| `id` | `uuid` | первичный ключ, генерируется базой |
| `title` | `text` | текст задачи, пустые строки запрещены `check` |
| `done` | `boolean` | отметка «выполнено», по умолчанию `false` |
| `created_at` | `timestamptz` | время создания, по умолчанию `now()` |

## Шаг 1. Supabase

1. Создайте проект на [supabase.com](https://supabase.com) (Free tier достаточно).
2. Откройте **SQL Editor**, вставьте целиком `db/schema.sql` и нажмите **Run**.
3. Проверьте политики:

   ```sql
   select cmd, policyname from pg_policies
   where schemaname = 'public' and tablename = 'tasks' order by cmd;
   ```

   Должно быть 4 строки: `SELECT`, `INSERT`, `UPDATE`, `DELETE`.
4. Скопируйте `Project URL` и публичный ключ: кнопка **Connect** в шапке
   проекта (там же готовые значения) либо **Settings → API Keys**.
   Подойдёт и новый ключ `sb_publishable_…`, и legacy `anon` (`eyJ…`).

> `service_role` / `sb_secret_…` не нужен нигде в проекте: он обходит RLS,
> и его утечка означает полный доступ к базе.

## Шаг 2. Локальный запуск (десктоп)

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
copy src\config.example.py src\config.py   # и вставить URL + anon key
flet run src/main.py
```

Проверка до облачной сборки — обязательный шаг: десктопный запуск даёт
traceback с номерами строк, а лог Actions — нет.

Дополнительно, без сети и без Flet-окна:

```powershell
python tests/smoke_ui.py     # подменяет Supabase заглушкой и «нажимает» кнопки
```

## Шаг 3. GitHub и секреты

В системе не предполагается установленный Git — подойдёт любой из вариантов:

- **через веб-интерфейс:** на github.com → *New repository* → *uploading an existing file*
  → перетащить папку (файл `src/config.py` загружать **не** нужно);
- **через Git:** `git init`, `git add .`, `git commit -m "init"`,
  `git branch -M main`, `git remote add origin <url>`, `git push -u origin main`.

Затем в репозитории: **Settings → Secrets and variables → Actions → New repository secret**

| Имя секрета | Значение |
|---|---|
| `SUPABASE_URL` | `https://<ref>.supabase.co` (без `/rest/v1`) |
| `SUPABASE_ANON_KEY` | публичный ключ: `sb_publishable_…` или legacy `anon` (`eyJ…`) |

Секреты нужны именно здесь: workflow на этапе сборки генерирует из них
`src/config.py`, поэтому ключи не попадают в git, но оказываются внутри APK.

## Шаг 4. Сборка APK

`.github/workflows/build-apk.yml` запускается на push в `main` или вручную
(*Actions → Build APK → Run workflow*) и делает:

1. `compileall` — быстрая проверка синтаксиса до тяжёлой сборки;
2. генерирует `src/config.py` из секретов;
3. `flet-dev/flet-build-action@v1` — собирает APK (Flutter и Android SDK
   ставит сам, кэширует между запусками);
4. выкладывает архив сборки артефактом **и** прикрепляет `.apk` к Release
   с тегом `build-<номер>`.

Скачать: вкладка **Actions → нужный запуск → Artifacts** (внутри zip лежит apk)
или **Releases → build-N → apk-файл**.

## Шаг 5. Установка на Android

Скачайте `.apk` на телефон → откройте файл → разрешите установку из этого
источника, если система спросит. После установки добавьте задачу, отметьте её
и удалите — все три операции видны в Supabase (**Table Editor → tasks**).

## Разбор проблем

### Проблема 1. Сборка падала на несовпадении версий Python

**Симптом.** `flet build apk` в Actions завершался ошибкой установки
зависимостей: собранный пакет `supabase`/`httpx` не находил wheel под
выбранную версию Python внутри APK.

**Как искал.** Сравнил три версии: локальную (`python -V`), из
`requires-python` и `bundled-python-version` в workflow. Они не совпадали:
локально 3.14, а зависимости ставились под другую версию.

**Решение.** Одна версия в трёх местах: `requires-python = ">=3.12,<3.14"`,
`bundled-python-version: "3.13"`, локальный venv на 3.13. Flet выбирает самую
старшую поддерживаемую версию, удовлетворяющую `requires-python`, поэтому
диапазон должен быть узким.

**Что понял.** `flet build` встраивает в APK собственный интерпретатор Python —
это не Python с телефона и не Python из runner'а; версия задаётся на этапе
сборки и должна совпадать с той, под которую есть wheels.

### Проблема 2. Сборка падала на шаге подготовки: `flet --version --json` вернул пустоту

**Симптом.** Job `build-apk` умирал за 20 секунд, ещё до Flutter:

```
##[error]Could not parse `flet --version --json` output: Expecting value: line 1 column 1 (char 0).
```

**Как искал.** Скачал лог упавшего шага (он отдаётся через подписанный
redirect, поэтому брал его отдельно от API-запроса) и прочитал строки до
ошибки: `uv` создал окружение из `pyproject.toml`, установил 55 пакетов, а
затем вызвал `flet --version --json` — пустой вывод. Пустой вывод у команды
означает не «неверный флаг», а «команды нет»: в Flet 1.x CLI вынесен в
отдельный пакет `flet-cli`, который ставится только с extra `[all]`
(или `[cli]`).

**Решение.** В `pyproject.toml` и `requirements.txt`:

```toml
"flet[all]==1.0.5"
```

Проверил локально до повторной сборки: после установки с `[all]` появляется
`flet.exe` и `python -m flet_cli.cli --version --json` отвечает
`{"flet": "1.0.5", "flutter": "3.44.8", ...}`.

**Что понял.** Для Flet 1.x «пакет библиотеки» и «CLI» — разные вещи;
действие `flet-build-action` требует именно CLI в окружении проекта. Заодно
это чинит и локальный `flet run`, поэтому совет «поставь flet» из старых
инструкций теперь недостаточен.

### Проблема 3. Список не обновлялся после изменения

**Симптом.** Задача добавлялась в Supabase, но на экране список не менялся,
пока не перезапустить приложение.

**Как искал.** Проверил порядок: запрос уходит (видно в Supabase → Logs),
данные меняются, значит проблема на стороне UI. Добавил `print(len(tasks))`
в `refresh()` — новые данные приходили.

**Решение.** Flet не перерисовывает экран сам после изменения контролов:
нужен `page.update()` в конце обработчика. В итоге `refresh()` — единственное
место, где перестраивается список, и он всегда заканчивается `page.update()`.

**Что понял.** Flet — не «магия поверх Flutter»: контролы в Python-объектах
меняются сразу, а на экран попадают только после `update()`. Поэтому все
изменения списка собраны в одну функцию, а не размазаны по обработчикам.

## Что я понимаю и могу защитить

- **Почему без бэкенда.** Supabase отдаёт REST API поверх PostgreSQL; для
  одной таблицы и учебного CRUD свой сервер — лишний слой. Плата за это —
  ответственность за RLS на клиенте.
- **Почему `anon`-ключ можно держать в APK.** Он публичный по дизайну: это
  не пароль, а идентификатор роли `anon`. Данные защищают политики RLS.
  `service_role` обходит RLS — его в APK быть не должно.
- **Почему RLS обязателен.** Роль `anon` имеет права на таблицу, но без
  политики RLS запрос вернёт пустой список (select) или ошибку `42501`
  (insert/update/delete). Политика `using (true)` разрешает всё — для
  учебного проекта допустимо, в реальном нужно `auth.uid() = user_id`.
- **Почему `src/config.py` генерируется.** В APK нет переменных окружения
  CI, поэтому значения должны попасть в файл на этапе сборки — но не в git.
- **Почему `upload-artifact` с `archive: false`.** Action уже отдаёт готовый
  zip; без этой опции файл упаковали бы второй раз.

## Ограничения (честно)

- Сетевые вызовы синхронные: на медленной сети интерфейс «замирает» на время
  запроса. Лечится `page.run_task`/потоком — оставлено как следующий шаг.
- Нет авторизации: все пользователи видят общие задачи (по условию задания).
- Нет офлайн-кэша: без сети список пустой и показывается ошибка.
- APK не подписан релизным ключом — подходит для установки вручную, не для
  Google Play.
